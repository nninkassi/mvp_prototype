# Стратегия тестирования и обеспечения качества (QA)
В проекте применен гибридный подход, сочетающий автоматизированное и ручное тестирование. Автоматизированные тесты эмулируют действия конечного пользователя через прямые HTTP-запросы к локальному серверу (`http://127.0.0.1:8000`), что позволяет верифицировать бизнес-процессы, корректность разграничения ролей и работу модулей системы.

**Инструментарий:** `pytest` (v9.0.3), `requests` (v2.31.0), `pytest-html` (v4.2.0) для визуализации отчетов.


## 1. Функциональное тестирование

Функциональное тестирование проверяет, что сервис выполняет заявленные требования. Особое внимание уделено негативным сценариям и разграничению прав доступа (RBAC).

### 1.1. Разграничение прав доступа (RBAC)
Проверка того, что неавторизованные пользователи не могут получить доступ к защищенным маршрутам. Система должна корректно прерывать выполнение и перенаправлять на страницу входа без создания побочных записей в БД.

|     Наименование   сценария                           |     Запрос                     |     Ожидаемый   результат                        |     Фактический   результат                                            |
|-------------------------------------------------------|--------------------------------|--------------------------------------------------|------------------------------------------------------------------------|
|     Доступ   к профилю без авторизации                |     GET   /profile/            |     Запрет   на доступ к профилю                 |     Перенаправление   на /login/ (HTTP 302)                            |
|     Добавление   товара в корзину без авторизации     |     POST   /add_to_cart/1/     |     Отклонение   запроса                         |     Перенаправление   на /login/ (HTTP 302), записи в БД не создано    |
|     Оформление   заказа без авторизации               |     POST   /checkout/          |     Отклонение   запроса                         |     Перенаправление   на /login/ (HTTP 302), заказ в БД не создан      |
|     Доступ   к статистике продавца без авторизации    |     GET   /seller/stats/       |     Запрет   на доступ к аналитике               |     Перенаправление   на /login/ (HTTP 302), данные не отображены      |
|     Доступ   к товарам продавца без авторизации       |     GET   /seller/products/    |     Запрет   на доступ к информации о товарах    |     Перенаправление   на /login/ (HTTP 302), данные не отображены      |
|                                                       |                                |                                                  |                                                                        |
### 1.2. Пользовательские сценарии (Buyer Flow)
Проверка основного пути покупателя: от регистрации и поиска до оформления заказа с валидацией CSRF-токенов и корректным сохранением данных.


|     Наименование   сценария                       |     Запрос                                        |     Ожидаемый   результат                                       |     Фактический   результат                                                   |
|---------------------------------------------------|---------------------------------------------------|-----------------------------------------------------------------|-------------------------------------------------------------------------------|
|     Регистрация   нового покупателя               |     POST   /register/                             |     Аккаунт   создан                                            |     Статус   200, запись в таблице User создана                               |
|     Фильтрация   товаров в каталоге               |     GET /catalog/?category=1                      |     Корректная   выдача товаров                                 |     Статус   200, в HTML-ответе найдены запрошенные товары                    |
|     Просмотр   карточки и добавление в корзину    |     GET /product/{id}/, POST   /cart/add/{id}/    |     Карточка   товара отображается, товар добавлен в корзину    |     Страница   товара загружена, запись в CartItem создана                    |
|     Оформление   заказа                           |     POST   /checkout/                             |     Заказ   создан                                              |     Статус   302 с направлением на /success/,   запись в Order создана        |
|     Деактивация   аккаунта                        |     POST /profile/delete/                         |     Статус   302 Found, деактивация аккаунта                    |     Статус   302 Found, сессия завершена, целостность данных не нарушена      |
|                                                   |                                                   |                                                                 |                                                                               |

### 1.3. Функционал кабинета продавца (Seller Flow)
Критически важная проверка изоляции данных: продавец должен иметь доступ к статистике и управлять только своим ассортиментом.

|     Наименование   сценария              |     Запрос                                                                                   |     Ожидаемый   результат                                                                                           |     Фактический   результат                                                                                                 |
|------------------------------------------|----------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
|     Доступ   к статистике                |     GET /seller/stats/                                                                       |     Страница   статистики загружается, навигация отображает элементы кабинета                                       |     Статус   200, в HTML-ответе страница статистики                                                                         |
|     Редактирование   товара продавцом    |     GET /seller/edit-product/{id}/,   POST /seller/edit-product/{id}/, GET /product/{id}/    |     Форма   редактирования загружается, данные обновляются в БД, новая цена отображается   на публичной странице    |     GET   вернул статус 200, POST вернул 200, в БД обновлена запись Product, на   /product/{id}/ отображается новая цена    |
|     Изоляция   товаров                   |     GET   /seller/products/                                                                  |     В   списке отображаются только товары текущего продавца                                                         |     Статус   200, в HTML-ответе присутствуют только товары, где поле seller совпадает id текущего   пользователя            |

## 3. Нагрузочное тестирование
Производительность оценивалась через эмуляцию последовательной и параллельной нагрузки. На основе эмпирических метрик был произведен теоретический расчет пропускной способности (RPS) для промышленной конфигурации (**Gunicorn**) с использованием **закона Литтла**, с учетом коэффициента масштабирования ($K_{scale} = 0.7$) и пиковых нагрузок ($K_{peak} = 4$).


|     Наименование   сценария                               |     Что   проверяется                                                                                 |     Ожидаемый   результат                                              |     Фактический   результат                                                   |
|-----------------------------------------------------------|-------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------|-------------------------------------------------------------------------------|
|     Базовый   замер времени отклика ключевых маршрутов    |     GET /catalog/, GET /product/{id}/,   GET /cart/ – замер   response.elapsed                        |     Среднее   время отклика <1.0 сек                                   |     Среднее   время HTTP-запроса 62 мс                                        |
|     Последовательная   нагрузка (50 запросов)             |     50   последовательных запросов к /cart/   – замер среднего, пикового времени и процента ошибок    |     Среднее   время <1.0 сек, ошибок нет                               |     Среднее   время 65 мс, пиковое 112 мс, error_rate = 0%                    |
|     Проверка   устойчивости к одновременным запросам      |     5   одновременных GET-запросов                                                                    |     Отсутствие   ошибок 500, сохранение приемлемого времени отклика    |     Общее   время 360 мс, ошибок 0%, данные не повреждены, error_rate = 0%    |
